## Data integrity and timer correctness

### 01. [HIGH] Settings import accepts any JSON object and silently replaces every setting with defaults

**Evidence level:** Runtime + source-traced  
**Locations:** `lib/services/settings_service.dart:226-234, lib/services/settings_service.dart:250-268, lib/main.dart:1456-1495`

**Evidence:** importFromJson only rejects non-objects: `final decoded = const JsonDecoder().convert(jsonString); if (decoded is! Map<String, dynamic>) return null; return AppSettings.fromJson(decoded);` (226-230). AppSettings.fromJson (lib/models/app_settings.dart:365-512) resolves every key through _string/_bool/_int/_double, each of which returns the *default* when the key is absent or of the wrong type. The caller then applies it unconditionally: main.dart:1472-1474 `_applyRestoredSettings(imported); ... 'Settings restored successfully!'` and main.dart:1488 `ref.read(settingsProvider.notifier).replace(normalized); ... _lsSave();` which persists the result. Failing inputs: a backup file from another app, `{}`, `[]`-less garbage like `{"version":2}`, or any JSON object without AppSettings keys → all 45 settings become defaults, saved to disk, and the user is told the restore succeeded.

**Consequence:** Total, silent loss of user settings (sound, volumes, night-mute hours, favorites, goal list) from one wrong-file pick in Settings → Restore; the confirmation dialog only warns that settings will be replaced, not that an unrecognised file is treated as 'all defaults'.

### 02. [HIGH] load() throws away a successfully loaded settings document when the write-back fails; main() then bootstraps pure defaults

**Evidence level:** Source-traced  
**Locations:** `lib/services/settings_service.dart:23-52, lib/services/settings_service.dart:54-80, lib/main.dart:305-313`

**Evidence:** load() starts with `await flush()` (line 24) — flush() returns the shared `_writeTail`, which is an *errored* future whenever the previous save failed (save() wraps only the *previous* link in catchError at 57-59; the new write's own failure stays on `_writeTail`). load() then ends with `await save(settings); return settings;` (50-51), and save() deliberately throws `StateError('SharedPreferences rejected settings snapshot write')` / `'...settings schema write'` when prefs returns false (65-74). main.dart wraps the whole call in one try/catch: `final settings = await SettingsService().load(...); SettingsNotifier.bootstrap(settings);` / `catch (...) { SettingsNotifier.bootstrap(AppSettings.defaults()); }` (306-312). So a write hiccup (or a prior failed write surfacing through flush()) discards an already-decoded, correct AppSettings and runs the session on AppSettings.defaults(); any later settings write (e.g. main.dart:1987-1990 `_lsSave()`, main.dart:1795-1815 `_setSpeechMaster`) then persists those defaults over the stored document.

**Consequence:** A single failed prefs write turns into a permanent, silent reset of all user settings; load() cannot distinguish 'I could not read' from 'I could not write back'.

**Review qualification:** Conditional on a preference write failing. No disk failure was injected; the exception-to-defaults path is source-traced.

### 03. [HIGH] Session logs are only produced by UI-driven timers; background/notification completions are never recorded

**Evidence level:** Source-traced  
**Locations:** `lib/main.dart:428; lib/main.dart:1993-2002; lib/main.dart:3303-3305; lib/main.dart:3729; lib/main.dart:2061; lib/main.dart:1748-1758; lib/main.dart:224-243`

**Evidence:** The only session start marker is in-memory: 'DateTime? _sessionStartTime;' (main.dart:428), set solely in startTimer ('if (taggingOn) _sessionStartTime ??= DateTime.now();', 3729) and _startPresetFromWidget (2061). Completion only logs when it is non-null: 'if (taggingOn && _sessionStartTime != null) { _logCurrentSession(_lastFinishedTimerDurationSeconds); }' (3303-3304). Nothing persists it (no prefs key references _sessionStartTime), and the non-UI start paths never set it: the notification 'Repeat' handler in the task isolate writes a running runtime ('runtime = TimerRuntime.running(... runId: runtime.runId ...)', 224-243) and the UI accepts it via 'if (type == 'runtime' ...) { await _applyTimerRuntime(TimerRuntime.fromJson(snapshot)); }' (1748-1758) -> _applyTimerRuntime (3129-3190) sets seconds/_activeTimerDurationSeconds but not _sessionStartTime.

**Consequence:** Study/non-study time is silently dropped: (a) a timer that runs to completion while the app process is dead is never logged (the FGS still shows 'Timer finished'); (b) a timer continued/restarted from the notification is never logged on completion; (c) any adoption of a running runtime after a process restart sets up the countdown with no session record. The Times dashboard/quick summary under-report usage.

**Repair direction:** Persist the session start together with the runtime: add 'sessionStartedAtEpochMs' to TimerRuntime (toJson/fromJson) set by _startPresetFromWidget/startTimer, and log from the state transition instead of from UI callbacks - call _logCurrentSession from _applyTimerRuntime (or from _completeTimerRun plus the restored-finished branch of _applyTimerRuntime) using the persisted start and the persisted durationSeconds, so every running->finished transition writes exactly one record.

### 04. [HIGH] Pause + resume then completion produces a self-inconsistent record and over-counts the day total

**Evidence level:** Runtime + source-traced  
**Locations:** `lib/main.dart:3736-3742; lib/main.dart:3729; lib/main.dart:3303-3304; lib/models/session_log.dart:43-60`

**Evidence:** Pausing logs the elapsed part: 'seconds = _timerRuntime.remainingAt(DateTime.now()); ... final elapsed = _activeTimerDurationSeconds - seconds; if (elapsed > 0) _logCurrentSession(elapsed);' (3738-3741) and _logCurrentSession nulls the start (2001). Resuming re-arms a NEW start ('if (taggingOn) _sessionStartTime ??= DateTime.now();', 3729) but keeps the FULL duration (_activeTimerDurationSeconds stays 1500 because of the guard at 3709-3713). When the timer then hits 0, the log uses the full duration: '_logCurrentSession(_lastFinishedTimerDurationSeconds)' where that is _activeTimerDurationSeconds (3274-3276, 3304). So the second record is startTime=resume time, endTime=completion, durationSeconds=full timer length.

**Consequence:** For a 25-min timer paused at 5 min: record 1 = 300 s; record 2 = startTime..endTime spanning 20 min but durationSeconds=1500. secondsWithin scales by overlap/wall (1500 * 1200/1200) and returns 1500, so the dashboard credits 1800 s (30 min) of study for 25 min of elapsed time. Any pause/resume cycle inflates the daily total by the paused amount.

**Review qualification:** The actual SessionLog.summarizeForDay implementation reported 2100 seconds for records produced by the 600-second pause + full 1500-second completion pattern. Active time was 1500 seconds.

**Repair direction:** On completion log the actually elapsed amount for the current session segment (elapsed = durationSeconds - remaining, or endTime - sessionStartTime) rather than _activeTimerDurationSeconds; keep _activeTimerDurationSeconds only for 'Repeat Same Timer' / display.

### 05. [HIGH] Chain/Pomodoro mode logs only the last segment as the whole session duration

**Evidence level:** Source-traced  
**Locations:** `lib/main.dart:3235-3250; lib/main.dart:3274-3276; lib/main.dart:3303-3304`

**Evidence:** Each chain step overwrites the run duration: 'chainIndex++; final nextSeconds = sequence[chainIndex] * 60; _activeTimerDurationSeconds = nextSeconds;' (3238-3240, and the runtime is re-created with durationSeconds: nextSeconds, 3241-3250). Only when the chain cannot advance does it record the total: '_lastFinishedTimerDurationSeconds = _activeTimerDurationSeconds > 0 ? _activeTimerDurationSeconds : sliderValue * 60;' (3274-3276), which is now the LAST segment, and that value is logged as the single session (3304) while _sessionStartTime is the chain start.

**Consequence:** A full 'Pomodoro 25-5x4' work chain (4 x 25 min = 100 min of wall-clock study) writes one SessionLog with startTime=chain start, endTime=chain end, durationSeconds=1500. SessionLog.secondsWithin (session_log.dart:43-60) then returns 1500, so the day summary reports 25 min for 100 min of study - a 4x under-count that grows with chain length.

**Repair direction:** Track the cumulative chain duration (e.g. accumulate '_chainElapsedSeconds += segmentSeconds' at 3240) and log that, or emit one SessionLog per completed segment inside the chain branch (with the segment's own start/end) and keep _lastFinishedTimerDurationSeconds for the 'Repeat Same Timer' button only.

### 09. [MEDIUM] TimerRuntime.fromJson has no invariant check: a stored 'running' runtime without endAtEpochMs yields a frozen, unfinishable timer

**Evidence level:** Runtime + source-traced  
**Locations:** `lib/models/timer_runtime.dart:107-131; lib/main.dart:3129-3190; lib/main.dart:3192-3198`

**Evidence:** fromJson accepts any combination: 'status: status' (decoded with orElse: idle for unknown names, 108-112) and 'endAtEpochMs: json['endAtEpochMs'] is num ? readInt('endAtEpochMs') : null' (123-125) - so 'running' + null endAt is representable. remainingAt then falls back to the static value: 'if (status != TimerRuntimeStatus.running || endAtEpochMs == null) { return remainingSeconds.clamp(0, 720 * 60); }' (65-66). _applyTimerRuntime starts a 250 ms ticker whenever status is running (3178-3180) and tick() returns immediately while remaining is unchanged: 'final remaining = _timerRuntime.remainingAt(DateTime.now()); if (remaining == previous) return;' (3194-3196).

**Consequence:** A runtime record that lost its endAtEpochMs (truncated/legacy snapshot, future writer) restores as a running timer whose display never moves and which never reaches remaining<=0, so _completeTimerRun never fires and the session never ends - the user must reset manually, and the persisted bad state survives restarts.

**Review qualification:** A running record without endAtEpochMs returned 60 seconds both now and an hour later.

**Repair direction:** Validate in fromJson: if status is running and endAtEpochMs == null, either recompute it (now + remainingSeconds) or coerce to paused/finished; also reject non-positive durationSeconds by mapping to idle.

### 10. [MEDIUM] System-clock adjustments change countdown and stopwatch duration

**Evidence level:** Runtime + source-traced  
**Locations:** `lib/models/timer_runtime.dart:64-71; lib/models/timer_runtime.dart:154-158; lib/main.dart:3192-3200; lib/main.dart:3017-3020`

**Evidence:** TimerRuntime.remainingAt subtracts now.millisecondsSinceEpoch from endAtEpochMs (64-70); StopwatchRuntime.elapsedMsAt subtracts startedAtEpochMs from the current wall clock (154-157). Neither uses a monotonic clock for live elapsed time.

**Consequence:** Any system clock adjustment (NTP correction, user change, timezone/DST only matters if the stamp were local - here it is epoch, so the real risk is an NTP/user jump) moves the countdown: a forward jump of 10 min finishes the timer 10 min early and fires 'Timer finished', a backward jump extends it; on the stopwatch a backward jump makes the clamp(0, ...) swallow the negative delta so the elapsed time freezes until wall time catches up again (and accumulatedMs is only written on pause, main.dart:3082-3093).

**Review qualification:** Epoch-based timing is not affected merely by DST or changing the displayed timezone. This finding concerns an actual system wall-clock jump. The diagnostic returned 0 seconds after a +1-hour jump and 3660 seconds after a -1-hour jump for a 60-second timer.

**Repair direction:** Keep the persisted epoch stamps for cross-process restore, but track the live session against a monotonic Stopwatch started/resumed alongside it (elapsed = accumulatedMonotonic; on resume, rebase once), or at minimum detect a backwards/forwards jump by comparing the monotonic and wall deltas and re-basing endAtEpochMs.

### 11. [LOW] Daily aggregation assumes every local day is exactly 24 hours

**Evidence level:** Source-traced  
**Locations:** `lib/services/session_log_service.dart:34; lib/models/session_log.dart:74; lib/models/session_log.dart:31-32; lib/models/session_log.dart:51-60`

**Evidence:** 'final dayEnd = dayStart.add(const Duration(days: 1));' (session_log_service.dart:34 and session_log.dart:74) and SessionLog persists local wall time with no offset: "'startTime': startTime.toIso8601String()" (31-32, parsed back with DateTime.parse at 44-45 -> local interpretation); secondsWithin prorates by wall overlap: 'return (durationSeconds * overlapMs / wallMs).round();' (51-60).

**Consequence:** On a 23 h/25 h DST day the day window is off by an hour (sessions are attributed to the neighbouring day and the prorated split is wrong), and because timestamps carry no UTC offset, moving the device to another timezone re-interprets every historical session - records shift to different calendar days and daily totals change retroactively.

**Review qualification:** This is distinct from clock-jump timing. Local DST days can be 23 or 25 hours; startTime/endTime serialization also omits explicit timezone/UTC normalization.

**Repair direction:** Build day bounds from calendar arithmetic (DateTime(date.year, date.month, date.day + 1)) instead of adding 24 h, and store timestamps as UTC ('startTime.toUtc().toIso8601String()') plus an explicit offset, converting to local only for display.

### 12. [MEDIUM] Typed preference reads are unguarded and throw on type mismatch (silent wrong default is not what happens here - it is a crash)

**Evidence level:** Source-traced  
**Locations:** `lib/services/timer_runtime_store.dart:24; lib/services/timer_runtime_store.dart:57; lib/services/timer_runtime_store.dart:102; lib/services/timer_runtime_store.dart:113; lib/services/timer_runtime_store.dart:129; lib/services/session_log_service.dart:20; lib/services/session_log_service.dart:74-77`

**Evidence:** Only reload() is wrapped: 'try { await prefs.reload(); } catch (_) {}' followed by an unwrapped read, e.g. 'final encoded = prefs.getString(runtimeKey);' (timer_runtime_store.dart:23-24), 'prefs.getInt(clockNextAtKey)' (102), 'prefs.getStringList(_prefsKey)' (session_log_service.dart:20, 77) and 'prefs.getBool(SettingsService.speechMasterOverrideKey)' (129). shared_preferences implements these as raw casts: 'int? getInt(String key) => _preferenceCache[key] as int?;' / 'String? getString(String key) => _preferenceCache[key] as String?;' / '... as List<String>?' (shared_preferences 2.5.4 lib/src/shared_preferences_legacy.dart:117-140) - a key holding a different type throws TypeError instead of returning null, so none of the defensive clamps in TimerRuntime.fromJson/AppSettings.fromJson ever run. The JSON parsing right next to these lines IS guarded (load():25-33), which hides the asymmetry.

## Suspicions rejected or narrowed during consolidation

- Signed public APK/AAB files do **not** expose private signing keys. No key rotation recommendation is justified merely by tracking signed artifacts. The keystore files observed on disk are ignored/untracked.
- Step-local environment is available to GitHub Actions step conditions. The initial agent claim that the keystore condition always skips was rejected against the runner implementation. The accepted finding concerns optional signing plus explicit debug-signing fallback, not environment scope.
- `dart:io` imports alone do not prove a web build fails. Web support was not built; no verified web compilation failure is listed.
- An epoch deadline does **not** change just because DST or the displayed timezone changes. Actual system-clock jumps and local-day-window errors are listed separately.
- UI language following the device and speech language being separately configurable is not inherently a defect. No requirement for a new language picker was inferred.
- Shared Aoede quote recordings are intentional project work. The accepted issue is misleading selected-voice status, not the existence of shared recordings.
- Absence of value equality is a reactive/performance issue here, not proof of corrupt data.
- Generated localization files match both 34-key ARBs. They were not reported as stale merely because generated files are committed.
- Countdown accounting is deadline-based, not tick-count-based; no invented periodic-timer drift bug is listed.
- Android foreground-service permissions/type declarations, POST_NOTIFICATIONS, exported receiver flags and minSdk/plugin requirements were inspected and found coherent.
- AppSettings field serialization/copyWith coverage and nullable-clearing convention are coherent. Lists are defensively normalized. Unknown enum values do not automatically crash.
- All declared audio asset directories exist; Malayalam clip mapping/assets were found complete by the motivation audit. The unused fonts and cross-platform runtime archive are separate concerns.
- Theme files mostly wrap a coherent token set. Three files alone do not justify claiming a broken theme architecture.
- Most timers/controllers/observers have cleanup; no blanket resource-leak claim is made.
- Ordinary Android Back can intentionally background an app. No demand to stop active background timers on every Back press was inferred.
